What the unit tests pin, by area:

- **Signature (7 cases).** Correct hex HMAC-SHA1 accepted; wrong secret,
  altered body, missing/empty/non-hex/short/long header all rejected;
  surrounding whitespace tolerated; a multi-byte (Cyrillic + astral) body
  verifies, so the UTF-8 encoding of the signed bytes is pinned, not assumed.
- **Fail-closed.** `drainSecret()` is null for unset, empty and whitespace-only;
  the route 503s in each case **and the mocked `@/db` spy records zero calls** —
  "never touched the database" is an assertion, not a hope.
- **Body-leak.** A forged signature returns exactly
  `{"error":"invalid signature"}` and no entry token, in both the unit test and
  the real-Postgres test, where it additionally writes no row.
- **Parsing.** NDJSON, JSON array, single object, empty body, and malformed
  lines/array members counted rather than thrown.
- **Projection.** A serialized normalized row contains no client IP, user agent,
  referer, ja3/ja4 digest or host; the key set is asserted exactly; query
  strings are stripped from both `path` and `proxy.path` (`/ask?q=…` → `/ask`).
- **Message pipeline.** Credential shapes redacted; ordinary prose untouched;
  the hash is over the redacted text (so a secret cannot survive in a hash
  preimage) and over the *full* message (so two messages differing past the clip
  differ); the clip is 2,000 code units and an astral pair straddling the
  ceiling leaves **no lone surrogate** — the #86 class, killed here by
  `wellFormedSlice` rather than avoided by luck.
- **Bounds.** Batch cap keeps the first N and counts the rest; intra-delivery
  duplicate ids collapse; self-ingested entries drop and never reach the INSERT
  params; oversized and unparseable bodies answer 200 (never a retryable
  status); a store failure answers 500; a sweep failure never breaks ingestion;
  the sweep is claimed at most once per interval.
- **Ruling 10.** The route's SQL trace contains no `cron_runs` and no
  `provider_state`; the fork itest re-asserts the `cron_runs` row count is
  unchanged across a real delivery.
- **No `GET`.** The route module exports `POST` only.

Real-Postgres additions (fork): the migration's exact column set and the three
indexes; `claim_must_have_source` still present after 0029 (9999 applied last);
full column round-trip with instants compared as **epochs**, never as
driver-rendered strings; redelivery stores 0; a 500-row batch in one statement;
the astral clip surviving the driver; the sweep deleting only rows *received*

## Rulings touched and how each is satisfied

- **Ruling 1 (legal).** `runtime_logs` holds our own log lines, redacted and
  clipped to 2,000 code units, and is internal-only — it is rendered on no
  user-facing surface and read only by `scripts/sqlq.ts`-style operator queries.
  No ISW prose or source full text is stored by construction; nothing about the
  ISW pipeline changed.
- **Ruling 3 (truth-in-UI).** Nothing here renders anywhere.
- **Ruling 4 (spend).** No paid-provider call exists on this path, so
  `SpendGuard` has nothing to guard. The *ordering* discipline is deliberately
  borrowed and written into both the design (§8) and `.env.example`:
  `LOG_DRAIN_SECRET` goes into Production **before** the receiver deploys, and
  an unset secret fails closed (503, no body read, no write) rather than open.
- **Ruling 5 (migrations).** 0029 is a new additive `CREATE TABLE` plus three
  indexes. No applied migration was edited or deleted; `9999` was neither
  renumbered nor moved and still sorts last (asserted on the fork).
- **Ruling 10 (`cron_runs`).** The receiver is not a cron. It opens no
  `cron_runs` row, never calls `withCronRun`, and therefore neither runs nor
  perturbs the #98 timeout sweep or the #103 map watchdog. The retention sweep
  was deliberately kept **out** of `startRun` for exactly this reason —
  `src/lib/usage/cron-run.ts:123` already carries two riders and runs at every
  cron start (≤15 minutes via `ingest:fast`); an unrelated `DELETE` for a table
  no cron reads has no business there.
- **Ruling 21 (authorization in the page).** This is an API route, not a page:
  no session, no user, nothing to gate with `requireAdmin` /
  `requireAcceptedUser`. **The drain signature is the entire authorization**,
  and it is verified before any parse, any allocation past the raw body, and any
  database call. It therefore takes **no row** in
  `src/integration/authz-page-gate.itest.ts`'s `ROUTES` table
  (`src/integration/authz-page-gate.itest.ts:85`) — that harness boots pages and
  asserts on rendered bodies, and there is no page here. The equivalent
  guarantee is asserted directly instead: a bad signature returns exactly the
  refusal object and writes no row (unit test + fork itest).

## Debt and risks

- **The receiver shares the fate of the deployment it observes.** A total outage
  loses exactly the lines that would explain it; Vercel's retry plus its
  errored-drain notification are the backstop. A hosted sink is the real fix if
  that case ever dominates. Recorded in the design §11.
- **The self-ingestion loop is bounded, not eliminated** — dropped at insert and
  starved by a log-silent handler, but still costing one request per batching
  interval until the operator adds the 0% sampling rule. Its filter is
  *path-keyed*, so it depends on the handler staying log-silent: a future
  `console.warn` in the route would fail no test and would slowly fill the table
  with the receiver's own noise. Worth a lint rule if that file grows.
- **Migration number.** Numbered **0030** to hold the order the program INDEX §4
  reserves (0028/0029 belong to step 13's benchmark-reports strand, whose PR is
  not yet open). The journal therefore has an idx gap 27 → 30, which is inert:
  `scripts/migrations-lib.ts` applies files in **filename sort order** and
  tracks them in `_migrations` by name, and `drizzle-kit generate` re-runs
  cleanly against the renumbered journal ("No schema changes"). **At rebase
  time, re-check:** if step 13 lands first, no change is needed; if this PR
  merges first, step 13b takes 0030. Either way the number is claimed at
  rebase, never renumbered after merge (ruling 5). Regenerated as 0029 on top of
  0028 at CP2b — the 0030 snapshot's `prevId` pointed at 0027.
- **Preview deployments are excluded** by the recommended registration —
  deliberate, and it means a preview-only defect leaves no drain evidence.
- **No alerting.** This table is evidence, not monitoring; alerting stays with
  `map-health` and the #103 watchdog, which read database state rather than log
  delivery.
- **`request_path` loses the cron discriminator** (`?which=fast`) to the
  query-string strip; recover it from `cron_runs.job`. This is the price of not
  storing `/ask?q=<user question>`.
- **Untested in production, necessarily.** Signature verification is pinned
  against the documented algorithm and against locally generated HMACs; the
  first real Vercel-signed delivery is the first end-to-end proof. The dashboard
  **Test** button on drain creation is that proof, and §8 step 5 makes checking
  it part of registration.

### For WS-3.6 (the shadow soak) — the SQL it will run

Full text in `docs/designs/LOG-DRAIN.md` §9; the three shapes are:

1. **Coverage** — `count(*)`, distinct `request_id`, distinct `deployment_id`,
   `count(*) FILTER (WHERE level IN ('error','fatal'))`, and
   `count(*) FILTER (WHERE status_code = -1)` over
   `logged_at >= $window_start AND logged_at < $window_end`. The last one is the
   crashed-with-no-response signature — invisible to every closeout before this
   table existed.
2. **Classification** — `GROUP BY message_sha256` over the window's
   `error`/`fatal` rows, with occurrence counts, first/last seen and a
   `left(message, 200)` sample. This is what makes the #86 closeout's standing
   instruction ("classify a residual `batchErrors` by signature from the runtime
   log") executable again.
3. **Correlation** — join `cron_runs` to `runtime_logs` on
   `request_path = '/api/cron/<job>'` and
   `logged_at ∈ [started_at, COALESCE(finished_at, started_at + <family ceiling>))`,
   where the ceiling comes from `JOB_MAX_DURATION_SEC` in
   `src/lib/usage/cron-run.ts` — precisely the window in which a run that left
   `finished_at IS NULL` must have died.

A soak closeout should report (1) as its coverage claim, (2) for classification,
and (3) for every run that went `ok=false`, degraded, or was swept. **A soak that
opens before the drain is registered still has no runtime-log coverage** — the
table only holds what a live drain delivers, and it is not retroactive.
