**Caveat A — the dry-run finality defect (revised prompt §4.1).** In dry mode
`DryRunReferenceReportRepository` buffers nothing, so `stored` is `[]` on every day and
`finalKey` falls back to `out.editions[0].editionKey`

error in the case under test. That is reasoning, not a measured property.

`editions == 1`. When a day has one edition, first-probe order and finality ordering select
the same edition necessarily, so caveat A cannot change these particular numbers: with
`multiEditionDays = 0`, `anchorNotFinalDays = 0` is arithmetic, not measurement. **The C5-m
question — how often the citation anchor differs from the daily-final edition on

## 7. Finding — the prompt's `env -u` migrate line targets PRODUCTION

**The single most important thing in this report.** Prompt §3 step 2 explicitly recommends
`env -u` *over* `VAR=`, and it is exactly backwards for this script.

`scripts/env.ts` calls `config({path: ".env.local"})` and `config()` **without `override`**.
dotenv declines to overwrite a variable that is **present** and sets one that is **absent** —
so unsetting a variable is precisely what invites `.env.local` to repopulate it.
`scripts/migrate.ts:8` then reads `DATABASE_URL_UNPOOLED ?? DATABASE_URL`. The documented
command therefore ran `runMigrations` against **production's unpooled endpoint**.

It failed `28P01` (password authentication failed). **The only reason it did not apply
0028/0029/0030 to production is that production's `DATABASE_URL_UNPOOLED` credential in
`.env.local` is stale — OPEN-TASKS #80.** #80 is currently load-bearing safety by accident;
fixing #80 without fixing this idiom arms the landmine. Nothing was written: authentication
fails before any statement, and production was re-verified at 29 migrations immediately
after.

Proven independently, without re-running the dangerous command, by replicating `env.ts`'s
two dotenv calls and printing which host `migrate.ts` would select: it selected a
production endpoint, not the fork.

Correct form, used for the real run: `DATABASE_URL="$FORK" DATABASE_URL_UNPOOLED="$FORK"`.
A present variable is the only variable dotenv will not touch. Filed as OPEN-TASKS #112 with
a proposed boundary guard in `scripts/migrate.ts` on the R4 `--base-ack` pattern.

## R.10 Fetch health — the 403 state suppresses REAL pages, correcting the 2026-09-07 mitigation

§8's amended bullet says to halt only if "a day that the `isw_reports` table shows as published
returns **no** edition at all — that would be the slug-shape hazard, not throttling."

**That trigger fired literally, and this session did not halt.** The reason, with the evidence
that separates the two causes:

- **It is not the slug-shape hazard.** Every one of the 46 `isw_reports` URLs in the window
  (23 `ir`, 23 `ru`) is exactly one of the shapes the probe generates:
  `iranUpdateUrlCandidatesForDate` (`src/lib/validation/run.ts:31-41`) emits
  `special-report-<md>`, `evening-special-report-<md>`, `morning-special-report-<md>`,
  `<md>`, and the window's `ir` URLs are all three prefix special-report forms; `iswUrlForDate`
  emits the single ROCA shape and every `ru` URL matches it. No shape is un-probed. (The
  June-2025 suffix form §0.6 warns about does not occur here.)
- **It is the host's 403 state — proven by a repeat, not inferred.** `roca` was run three
  times over the identical 23 days: `publishedDays` **6 → 6 → 13**, `probeFailedDays`
  **17 → 17 → 10**. Publication is a fixed historical fact, so at least 7 of pass 1's 17
  `probe_failed` days were false; and since `isw_reports` shows all 23 `ru` days published,
  **all 17 were false**. A `probe_failed` day in these runs means "we could not tell", nothing
  more.
- **The 404 → 403 threshold reproduces the August measurement exactly.** Reconstructing from
  the arithmetic `probeFailures = (probes with status ≠ 404) − editions`
  (`edition-discovery.ts:359`): the `iran_update` pass-0 run served **20 clean 404s** — 3 on
  02-28, 2 on each of 03-01…03-08, 1 on 03-09 — and then **not one more clean 404 in the
  remaining 55 network probes**. The 2026-09-08 August re-run put the trip at "roughly 20
  not-found requests". It is 20 here.
- **Real pages are still served during the tripped state, but not reliably.** Disk-cache
  mtimes settle this: every cached page for this window was written *during this run*
  (14:36:24Z → 14:40:20Z) — the window was uncached beforehand — and 12 of the 21 were
  fetched *after* the trip. So the 2026-09-07 re-run's n=1 observation replicates. But the
  same run left 25 known-published URLs undiscovered, and the roca 6 → 13 recovery shows the
  outcome is probabilistic. **The mitigating sentence in that earlier section — "a genuine
  second edition would most likely have been served" — is too strong and is corrected here.**

**Consequence for C15/(f14), which is the part that matters beyond this measurement.** Because
`isCleanNotFound` accepts only `status === 404`, a 403 day can never satisfy
`everyProbeCleanNotFound`, so `publication_gap` is unreachable on any day probed under the
tripped state — which, at a 20-request budget, is most of any window longer than about a week.
Read one way that is accidental protection: this host cannot manufacture a phantom gap through
throttling. Read the other way, the C15 confirmation instrument is inert in practice, and
`probe_failed` accumulates as an ambiguous status that means both "no such page" and "we were
throttled". Both readings are worth having in front of WS-3.6 before the soak predeclares
thresholds against these statuses.
