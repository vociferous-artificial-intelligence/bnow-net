**Caveat A — the dry-run finality defect (revised prompt §4.1).** In dry mode
`DryRunReferenceReportRepository` buffers nothing, so `stored` is `[]` on every day and
`finalKey` falls back to `out.editions[0].editionKey`
(`src/lib/isw/edition-discovery.ts:501-503`) — i.e. **probe order**, which is the exact
variable C5-m exists to test. Per the revised §4.1 this is **not** cleanly "biased toward
zero": it miscounts in both directions. A **net undercount** is expected by correlation, not
by rule — the anchor is matched by canonical URL against `isw_reports` rows production wrote
using its own probe order, so anchor and probe-first tend to coincide, concentrating the
error in the case under test. That is reasoning, not a measured property.

**Caveat B — the denominator is zero anyway.** On every published day in both series
`editions == 1`. When a day has one edition, first-probe order and finality ordering select
the same edition necessarily, so caveat A cannot change these particular numbers: with
`multiEditionDays = 0`, `anchorNotFinalDays = 0` is arithmetic, not measurement. **The C5-m
question — how often the citation anchor differs from the daily-final edition on
multi-edition days — has an empty denominator in this window and is therefore unanswered by

(§6) is the open question, and it is step 24's to weigh.

**`publicationGapDays = 0` is structurally meaningless on pass 0.** `confirmGapEligible()`

## 7. Finding — the prompt's `env -u` migrate line targets PRODUCTION

**The single most important thing in this report.** Prompt §3 step 2 explicitly recommends
`env -u` *over* `VAR=`, and it is exactly backwards for this script.

`scripts/env.ts` calls `config({path: ".env.local"})` and `config()` **without `override`**.
dotenv declines to overwrite a variable that is **present** and sets one that is **absent** —
so unsetting a variable is precisely what invites `.env.local` to repopulate it.
`scripts/migrate.ts:8` then reads `DATABASE_URL_UNPOOLED ?? DATABASE_URL`. The documented
command therefore ran `runMigrations` against **production's unpooled endpoint**.

It failed `28P01` (password authentication failed). **The only reason it did not apply
0028/0029/0030 to production is that production's `DATABASE_URL_UNPOOLED` credential in
`.env.local` is stale — OPEN-TASKS #80.** #80 is currently load-bearing safety by accident;
fixing #80 without fixing this idiom arms the landmine. Nothing was written: authentication
fails before any statement, and production was re-verified at 29 migrations immediately
after.

Proven independently, without re-running the dangerous command, by replicating `env.ts`'s
two dotenv calls and printing which host `migrate.ts` would select: it selected a
production endpoint, not the fork.

Correct form, used for the real run: `DATABASE_URL="$FORK" DATABASE_URL_UNPOOLED="$FORK"`.
A present variable is the only variable dotenv will not touch. Filed as OPEN-TASKS #112 with
a proposed boundary guard in `scripts/migrate.ts` on the R4 `--base-ack` pattern.

### What the failures actually are — measured, not inferred

`probeFailures` counts any probe that is neither a clean 404 nor an edition
(`edition-discovery.ts:359`), and `isCleanNotFound` accepts **only** `status === 404`
(`:226-228`). Three findings, each with its evidence:

1. **The failing probes are HTTP 403, not 404 and not a timeout.** One diagnostic GET on a
   known-nonexistent slug returned `status=403, 0 redirects, 9,661 bytes`. `politeFetch`
   retries only on 429 or ≥500 (`fetch-cache.ts:59-62`), so a 403 returns immediately on the
   first attempt — no retry storm, and a deterministic result.
2. **`politeFetch`'s spacing was fully honoured in-process.** Only 200 bodies are disk-cached,
   so on each published day exactly one shape (the real ~410 KB page) was a cache hit and the
   other three went to the network: 25 cache hits + 99 network fetches × 2.1 s = 208 s
   predicted, against a **measured 207 s**. The arithmetic leaves no room for a violated
   spacing interval.
3. **The 404 → 403 switch is a deterministic threshold, not random throttling.** Both runs show
   the same shape: days 08-01→08-06 clean (`probeFailures=0`, 18 network fetches, all 404),
   then 08-07 partial (`probeFailures=1`), then 403 for the remainder. The host flips after
   roughly 20 not-found requests and stays flipped for the rest of the run. Confirmed
   post-run: the 2026-08-03 shape that returned a clean 404 *during* this very run returned
   **403** when re-requested minutes after it finished.

### Correcting §6

- **§6's concurrency explanation is not needed to produce 79/124 and is refuted as its
  cause.** A single session at the documented ≥2.1 s spacing reproduces the figure exactly.
  §6's narrower observation — that the concurrent re-run showed `probeFailures=3` on days
  08-01→08-06, which *both* clean runs show as 0 — stands, and is consistent with the
  threshold model: a second fetcher pushes the not-found count past the trip point sooner.
- **The consequence for the measurement is milder than §6 concluded, for a specific reason.**
  §6 warned that "a second edition sitting on a shape whose probe failed would not have been
  seen". Measured against that: **a real page still returns 200 while the host is in its
  tripped state** — `iran-update-august-20-2026` returned `200, 410,463 bytes` on a request
  made after the trip, in the same minute a nonexistent shape returned 403. So the 403 is a
  not-found response under load, not a blanket block, and a genuine second edition would
  most likely have been served.
- **It is still not proven, and `multiEditionDays = 0` stays a soft negative.** No
  multi-edition day exists anywhere in the sample to test that inference against — which is
  the very quantity under measurement. The honest form for step 24 is: *no multi-edition day
  was observed, on a measurement that is fully reproducible, where 63.7% of probes returned
  an indeterminate status but real content was verifiably still served during that state.*

### A WS-3 finding this produced (for step 18's register, remediation step 23)

`isCleanNotFound` equating "does not exist" with `status === 404` alone is too narrow for this
host. understandingwar.org answers **403** for not-found once a modest request threshold is
crossed, so the metric conflates "the shape genuinely does not exist" with "we could not tell"
— and it does so on the majority of days in any window longer than about a week. Two
consequences: `probeFailures` overstates real trouble, and `confirmGapEligible`
(`:230-243`) can never confirm a publication gap on such days, because a 403 day is not an
all-404 day. This is a defect in the module step 14 owns, not in this measurement. **Not fixed
here** — this step measures and reports.
