### The shape, and why each part of it is what C6 = (b) requires

**`conflict_validation_observations`** — `id`, `conflict_id`, `reference_edition_id`,
`series`, `report_date`, `edition_key`, `evaluation_kind`, `contributing_digest_ids`,
`result`, `unit_attribution`, `matcher_rung`, `matcher_model`, `votes_k`, `dispatch`,
`methodology_epoch`, `lane_taxonomy_version`, `evidence_policy_version`,
`lane_classifier_version`, `actor_roster_version`, `scope_version`, `gazetteer_version`,
`unit_flags_version`, `edition_norm_version`, `daily_final_policy`, `extractor_versions`,
`registry_version`, `window_end_source`, `run_group_key`, `cron_run_id`, `observed_at` —
the §3.1b list verbatim, including the C3 (`unit_attribution`), C7 (`gazetteer_version`)
and C13 (`unit_flags_version`) columns.

1. **No overwrite path exists anywhere.** There is no unique key on
   `(conflict_id, reference_edition_id)`, no `ON CONFLICT` clause in the one INSERT, and
   no `UPDATE`/`DELETE`/`MERGE` statement in the module at all — pinned by a source scan
   that strips comments first (so the prose explaining the rule cannot satisfy it).
2. **The only unique key is a partial per-invocation duplicate guard:**
   `(conflict_id, reference_edition_id, cron_run_id) WHERE cron_run_id IS NOT NULL`.
   Repeated runs of the same day under different `cron_runs` rows APPEND; a row written
   outside a cron (`cron_run_id` NULL) is unconstrained.
3. **The headline is derived at read time.** There is deliberately no headline column:
   `latestObservationsFor` takes `DISTINCT ON (reference_edition_id) … ORDER BY
   reference_edition_id, observed_at DESC, id DESC` and reads `headline` off the stored
   result. The older rows stay available as the soak's variance sample.
4. **Both FKs keep `ON DELETE NO ACTION`.** Deleting a scored edition or its bookkeeping
   row is BLOCKED and visible, never cascaded into silent observation loss nor nulled into
   a silently unattributed row.

### Two deliberate strengthenings beyond the plan's wording

Both are recorded here because they are the parts a reviewer should attack.

1. **The row is a PROJECTION of the result, not a second set of facts.** §3.1b names
   `persistObservation(query, row)` without saying where each column's value comes from.
   Every column the scored result already determines — conflict, series, report date,
   edition key, evaluation kind, matcher rung/model/k, the five in-result version stamps,
   extractor versions, window-end source, run group key — is READ OFF the result rather
   than accepted from the caller, so a row cannot claim `keyword` while the result it
   stores says `llm-majority`. The caller supplies only what the result genuinely does not
   know: `referenceEditionId`, `cronRunId`, `contributingDigestIds`, `unitAttribution`,
   `dispatch`, and the five out-of-result stamps (`gazetteerVersion`, `unitFlagsVersion`,
   `editionNormVersion`, `dailyFinalPolicy`, `registryVersion`). Step 19 therefore cannot
   introduce a row/result disagreement even by mistake.
2. **A ruling-1 prose audit at the persistence boundary, in both directions.** §3.1b's test
   line asks that "a result carrying a sentinel string anywhere outside allowed id/enum
   fields is refused before any write"; `assertNoProseInStoredResult` is the mechanism.
   Every string in the serialized result, **object keys included**, must be a bounded
   machine token — `/^[A-Za-z0-9._:/|=+@-]*$/`, ≤256 chars, no whitespace — with exactly
   two exceptions the result contract already gates: `headlineLabel` must equal
   `CONFLICT_HEADLINE_LABEL`, and `window.cutoffAtRaw` / `window.publishedAtRaw` must
   satisfy `isPersistableRawAnchor` (`eval-profile.ts:387`). The alphabet was **measured,
   not guessed**: a walk over every string in the committed goldens — real, byte-pinned
   scorer output — finds those two fields are the only non-token strings the corpus
   produces. The audit also refuses non-finite numbers and any non-plain object (a `Date`
   or class instance), so nothing can reach `jsonb` through a shape no validator sees. The
   same audit runs on READ, so a row that somehow held prose is refused on the way out
   rather than rendered — the `parseStoredAnchorJournal` discipline PR #63 established.

## Debt and risks

- **The app-layer non-retrospective refusal is unreachable today.** `persistObservation`
  calls `assertPersistableConflictResultV1` first, as §3.1b says, and that gate already
  refuses a scored non-`retrospective` result (register #5), so the store's own twin never
  fires. It is kept deliberately — the same belt-and-braces pattern `eval-profile.ts` uses
  for the scorer's zero-denominator refusal — because when the reviewed capture path lifts
  the register-#5 refusal, the observation table's retrospective-only contract must survive
  that change on its own. Behaviourally covered (a non-retrospective result is refused with
  no write); the *twin's own branch* is not independently exercised. Reordering it ahead of
  the gate would make it reachable, at the cost of the gate no longer being provably first.
- **Fail-closed reads are all-or-nothing.** One poisoned row makes `latestObservationsFor`
  throw for the whole page rather than skipping the row. That is the intended direction
  (never render an unvalidated stored result), but step 24's view must handle the throw as
  a surface-level "unavailable", not a 500.
- **The stored-token alphabet is deliberately tight.** A live `sourceDomain` or theater
  label containing a character outside `[A-Za-z0-9._:/|=+@-]` would be REFUSED, not
  truncated or escaped. Measured safe against every committed golden, and hostnames and
  `host/handle` source labels fit — but step 19's first fork run against real claims is the
  moment this is genuinely proven, and the fix if it fires is to widen the alphabet
  deliberately (with the reason recorded), never to drop the audit.
- **Postgres truncates the edition FK's name.** drizzle-kit emits
  `conflict_validation_observations_reference_edition_id_benchmark_report_editions_id_fk`;
  Postgres stores the 63-byte prefix
  `conflict_validation_observations_reference_edition_id_benchmark`. The itest asserts the
  STORED name. Inert today (the migration is marker-skipped, and drizzle compares
  snapshots, not the database), but any future tool that diffs live constraint names
  against the migration text will see a mismatch.
- **`observed_at` defaults to `now()`, which is transaction time.** Two observations
  written inside one transaction would share an instant; the reader's `id DESC` tie-break
  is what keeps "latest" total. Step 19 writes one observation per edition per run, so this
  is a bound, not a live hazard.
- **No `conflict_validation_observations` row has ever been written outside a fork.** The
  table is additive, starts empty, and nothing in production imports the conflict layer.
  N2 still stands: once step 14's route deploys, a manual `GET` with `CRON_SECRET` would be
  a production write and remains forbidden until the WS-3.6 scheduling entry.
- **`fileParallelism: false` is now load-bearing twice over.** Flipping it would let two
  itests race on the first application of 0028 *and* 0030 on a fresh fork.
